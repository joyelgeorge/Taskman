Four bugs a 595-test suite missed

All four were in my own codebase. All four passed every test. All four would have broken in production, and one of them silently threw away data for months.

1 · A query that could never run

An untyped parameter made PostgreSQL read a timestamp as an interval, so the query died with operator does not exist: timestamp with time zone <= interval. The feature could never have worked in production. Not once.

Why the tests missed it: in-memory mode never executes the SQL. git show 6780227

2 · A table nothing ever created

Code inserted into outreach_drafts. No migration created it. The insert was wrapped in a catch that fell back to an in-process Map and returned ok: true — so every record was discarded when the process exited, and the caller was told it saved.

Why the tests missed it: the fallback made failure look like success. git show 3d0da3e

3 · A constraint the app broke on every call

A CHECK allowed two values. The UI sent a third. Every request to that endpoint returned 500 against a real database.

Why the tests missed it: memory mode enforces no constraints. git show 66a3773

4 · A date that came back a day early

node-postgres parses a DATE at local midnight, so calling toISOString() shifts it backwards for every timezone east of Greenwich. A record written for the 2nd read back as the 1st.

Why the tests missed it: correct in UTC. Wrong for most of the world. git show 22a1dc2

All four had one cause.

The tests exercised a different storage backend than production used. An AI writes both an in-memory fallback and the real database path, and the suite only ever runs the easy one — so the suite goes green while the path that ships stays unverified.

It is not a rare failure. It is the default shape of an AI-written application, and no amount of additional tests against the same fallback will find it.
